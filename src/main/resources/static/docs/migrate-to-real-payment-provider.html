Migrar StreamBox desde Mock Payment Service a una pasarela real

Esta guía explica cómo adaptar el patrón de StreamBox Demo para integrarlo con una pasarela de pagos real.

StreamBox Demo usa Mock Payment Service para aprender el flujo completo sin procesar dinero real. En una aplicación productiva, el mock se reemplaza por un proveedor real como Mercado Pago, Stripe, PayPal u otro.

La migración no consiste solamente en cambiar una URL. Hay que revisar cliente HTTP, SDK, DTOs, webhooks, validación de firma, estados internos, base de datos, idempotencia, seguridad, términos comerciales y pruebas de sandbox.

Idea central

StreamBox Demo actual
  ↓
MockPaymentClient
  ↓
Mock Payment Service

Aplicación real
  ↓
PaymentProviderClient
  ↓
MercadoPagoClient / StripeClient / PayPalClient / Otro proveedor
  ↓
Pasarela real

El objetivo es conservar la arquitectura útil de StreamBox, pero reemplazar las piezas específicas del mock por piezas adaptadas al proveedor real.

Qué se conserva del patrón de StreamBox

Algunas ideas de StreamBox son buenas y conviene mantenerlas.

Idea Por qué se conserva
Cliente dedicado para hablar con el proveedor Evita llamadas HTTP dispersas en controllers y servicios.
Estado interno propio La app necesita saber qué plan tiene cada cliente, más allá del proveedor.
IDs externos guardados Permiten relacionar pagos y suscripciones internas con recursos del proveedor.
Webhook receiver Permite reaccionar a eventos que ocurren fuera del flujo inmediato del usuario.
Validación de firma Evita procesar eventos falsos.
Consulta posterior al proveedor Evita confiar ciegamente en el body del webhook.
Mapeo de estados Permite desacoplar el dominio interno del vocabulario del proveedor.
Registro de webhooks recibidos Ayuda a depurar, auditar e implementar idempotencia.

Qué cambia al usar una pasarela real

En StreamBox Demo Con pasarela real
MockPaymentClient Cliente propio del proveedor o SDK oficial encapsulado.
Tarjetas ficticias Checkout hospedado, tokenización o componentes seguros.
MockPaymentWebhookController Controller de webhooks del proveedor real.
WebhookSignatureVerifier del mock Validador de firma según documentación oficial del proveedor.
DemoStore Base de datos real con transacciones y constraints.
Estados simples del mock Estados reales del proveedor, a veces más numerosos y complejos.
Eventos educativos Logs estructurados, auditoría y monitoreo.

Crear una interfaz PaymentProviderClient

En la demo, StreamBox depende directamente de MockPaymentClient. Para una aplicación real, conviene crear una interfaz propia. 

public interface PaymentProviderClient {

    ProviderSubscriptionResponse createSubscription(CreateProviderSubscriptionRequest request);

    ProviderSubscriptionResponse getSubscription(String providerSubscriptionId);

    ProviderPaymentResponse getPayment(String providerPaymentId);

    void cancelSubscription(String providerSubscriptionId);

    void changePlan(String providerSubscriptionId, ChangeProviderPlanRequest request);
}

Después se puede tener una implementación para el mock y otra para el proveedor real: 

@Component
public class MockPaymentProviderClient implements PaymentProviderClient {
    ...
}

@Component
public class MercadoPagoPaymentProviderClient implements PaymentProviderClient {
    ...
}

@Component
public class StripePaymentProviderClient implements PaymentProviderClient {
    ...
}

Ventaja

El servicio de billing no necesita saber si abajo hay un mock, un SDK oficial o llamadas HTTP directas. 

BillingService
  ↓
PaymentProviderClient
  ↓
Implementación concreta
Esta abstracción evita que toda la aplicación quede acoplada a una sola pasarela. Incluso si inicialmente se usa un único proveedor, la separación mejora el diseño.

Separar DTOs internos y DTOs del proveedor

En StreamBox Demo ya existe una separación entre DTOs propios y DTOs del mock. Al migrar a un proveedor real, conviene mantener esa idea. 

dto/
  CreateSubscriptionRequest.java
  CreateSubscriptionResponse.java
  PaySubscriptionRequest.java
  StartSubscriptionRequest.java
  StartSubscriptionResponse.java

dto/provider/
  CreateProviderSubscriptionRequest.java
  ProviderSubscriptionResponse.java
  ProviderPaymentResponse.java

dto/mercadopago/
  MercadoPagoCreatePreapprovalRequest.java
  MercadoPagoPreapprovalResponse.java

dto/stripe/
  StripeCheckoutSessionResponse.java
  StripeSubscriptionResponse.java

En el flujo actual de StreamBox, CreateSubscriptionRequest representa el paso de suscribirse y PaySubscriptionRequest representa el paso de pagar una suscripción existente. StartSubscriptionRequest puede quedar como ejemplo de flujo combinado o compatibilidad legacy.

Qué evitar

No conviene usar directamente los objetos externos del proveedor como entidades internas. 

No ideal:
BusinessSubscription guarda todo el JSON completo del proveedor como modelo principal.

Mejor:
BusinessSubscription guarda campos internos importantes.
Provider raw payload se guarda aparte si hace falta auditoría.

Adaptar SubscriptionService a un BillingService real

En StreamBox Demo, SubscriptionService crea la suscripción interna, llama al mock, guarda el ID externo, paga suscripciones existentes, procesa pagos y webhooks.

En una aplicación real podría convertirse en algo como: 

BillingService
SubscriptionBillingService
BusinessSubscriptionService
PaymentWebhookProcessingService

Flujo recomendado para crear una suscripción

1. Validar usuario autenticado.
2. Validar plan elegido.
3. Crear suscripción interna CREATING.
4. Crear recurso en el proveedor real.
5. Guardar providerSubscriptionId o providerCheckoutSessionId.
6. Cambiar la suscripción interna a PENDING si el proveedor respondió correctamente.
7. Devolver URL de checkout, client secret o estado inicial.
8. Ejecutar el pago como paso separado o redirigir al checkout.
9. Esperar confirmación por webhook.
9. Activar internamente solo cuando el proveedor confirme pago válido.

Importante

En muchas pasarelas reales, el pago puede no ocurrir inmediatamente en el mismo request. Puede haber redirección a checkout, autenticación adicional, pago pendiente, revisión antifraude o confirmación posterior por webhook. 

No asumir:
createSubscription() = usuario activo inmediatamente

Mejor:
createSubscription() = estado interno PENDING
paySubscription() o checkout = intento de pago
webhook confirmado = estado interno ACTIVE

Adaptar webhooks reales

En StreamBox Demo el endpoint es: 

POST /api/webhooks/mock-payment

Con un proveedor real se podría tener: 

POST /api/webhooks/mercado-pago
POST /api/webhooks/stripe
POST /api/webhooks/paypal

O un endpoint genérico: 

POST /api/webhooks/payments/{provider}

Flujo recomendado

1. Recibir webhook.
2. Extraer headers.
3. Guardar evento recibido en estado RECEIVED.
4. Validar firma u origen.
5. Rechazar o marcar inválido si falla validación.
6. Verificar idempotencia.
7. Consultar recurso actualizado al proveedor.
8. Actualizar pago o suscripción interna.
9. Marcar evento como PROCESSED.
10. Responder 2xx si corresponde.

Tabla sugerida

payment_webhook_event
  id
  provider
  provider_event_id
  request_id
  type
  action
  data_id
  valid_signature
  processed
  processing_error
  payload_raw
  received_at
  processed_at

Validación de firma

El validador de StreamBox Demo usa HMAC SHA-256 con un formato propio del mock. En una pasarela real, hay que usar el mecanismo oficial del proveedor.

Proveedor Qué revisar
Mercado Pago Headers de notificación, validación de origen/firma, consulta posterior del recurso.
Stripe Webhook signing secret, header de firma y construcción oficial del evento.
PayPal Validación de webhook según API o SDK oficial.
Otro proveedor Documentación oficial de webhooks, firma, certificados o secret compartido.
No reutilices literalmente el algoritmo de firma del mock para un proveedor real. El patrón se conserva, pero la implementación debe seguir la documentación oficial de la pasarela.

Mapear estados externos a estados internos

StreamBox Demo mapea estados del proveedor a estados propios. Esta idea debe mantenerse. 

Proveedor real
  approved / authorized / paid / succeeded
  ↓
Estado interno
  ACTIVE / APPROVED

Ejemplo de estados internos de suscripción

PENDING
ACTIVE
PAYMENT_FAILED
PAUSED
CANCELLED
EXPIRED
REFUNDED
DISPUTED

Ejemplo de estados internos de pago

PENDING
APPROVED
REJECTED
IN_PROCESS
REFUNDED
CHARGEBACK
CANCELLED
UNKNOWN

Los estados internos deben representar lo que la aplicación necesita para tomar decisiones, no solo copiar exactamente los nombres del proveedor.

Reemplazar DemoStore por base de datos

DemoStore sirve para la demo, pero no para producción. Al migrar a una app real, debería reemplazarse por entidades, repositorios y migraciones.

Entidades sugeridas

BusinessSubscription
BusinessPayment
PaymentWebhookEvent
PaymentAuditEvent
PlatformPlan

Repositorios sugeridos

BusinessSubscriptionRepository
BusinessPaymentRepository
PaymentWebhookEventRepository
PlatformPlanRepository

Constraints importantes

UNIQUE(provider_subscription_id)
UNIQUE(provider_payment_id)
UNIQUE(provider_event_id)
UNIQUE(request_id)

Por qué importan

Los webhooks pueden llegar más de una vez. Los retries pueden duplicar requests. La base de datos debe ayudar a impedir duplicaciones.

Idempotencia

Una integración de pagos debe tolerar eventos repetidos. 

Mismo webhook recibido dos veces
  ↓
Mismo provider_event_id
  ↓
Procesar una sola vez

También debe tolerar pagos ya registrados: 

Mismo provider_payment_id
  ↓
No crear otro pago interno

Estrategia recomendada

  1. Guardar el evento recibido antes de procesarlo.
  2. Usar un identificador único del proveedor.
  3. Crear constraints únicos.
  4. Procesar dentro de una transacción.
  5. Marcar el evento como procesado al final.
  6. Si llega repetido, devolver respuesta exitosa sin duplicar efectos.

Frontend y checkout real

StreamBox Demo muestra tarjetas ficticias en un select porque está integrado con un mock. En una aplicación real, el frontend no debería manejar tarjetas de esa manera.

Opciones frecuentes

Opción Descripción
Checkout hospedado El usuario paga en una página del proveedor.
Checkout embebido/tokenizado El proveedor entrega componentes seguros para capturar datos.
SDK frontend El frontend obtiene tokens o confirma pagos sin exponer datos sensibles al backend.
API directa Mayor control, pero más responsabilidad de seguridad y cumplimiento.
Para reducir riesgo, conviene evitar que el backend de la aplicación toque números completos de tarjeta o códigos de seguridad.

Variables de entorno reales

Las variables de StreamBox Demo deberían evolucionar al usar una pasarela real.

Ejemplo conceptual

PAYMENT_PROVIDER=mercado-pago
PAYMENT_PROVIDER_BASE_URL=https://api.proveedor.com
PAYMENT_PROVIDER_ACCESS_TOKEN=...
PAYMENT_PROVIDER_PUBLIC_KEY=...
PAYMENT_PROVIDER_WEBHOOK_SECRET=...
APP_PUBLIC_BASE_URL=https://app.example.com
APP_WEBHOOK_BASE_URL=https://api.example.com

Buenas prácticas

  • No commitear credenciales reales.
  • Separar credenciales sandbox y producción.
  • Usar variables de entorno o secret manager.
  • No mostrar secrets en la UI.
  • No imprimir tokens en logs.
  • Rotar credenciales si se filtran.

Plan de migración recomendado

Una forma ordenada de migrar sería:

  1. Crear una interfaz PaymentProviderClient.
  2. Hacer que MockPaymentClient implemente esa interfaz.
  3. Renombrar el servicio de demo hacia un nombre más general, como BillingService.
  4. Crear entidades reales en base de datos.
  5. Crear migraciones.
  6. Crear tabla de webhooks recibidos.
  7. Agregar constraints únicos.
  8. Agregar idempotencia transaccional.
  9. Crear implementación del proveedor real.
  10. Configurar credenciales sandbox.
  11. Adaptar el frontend al checkout real.
  12. Implementar webhook real.
  13. Validar firma según el proveedor.
  14. Probar pagos aprobados, rechazados, pendientes y cancelados.
  15. Recién después pasar a credenciales productivas.

Checklist antes de salir del mock

  1. La app tiene entidades reales de suscripción y pago.
  2. La app guarda IDs externos del proveedor.
  3. La app tiene tabla de webhooks recibidos.
  4. La app valida firma de webhooks.
  5. La app consulta el recurso actualizado después del webhook.
  6. La app procesa webhooks de forma idempotente.
  7. La app no guarda tarjetas reales.
  8. La app usa HTTPS en entornos públicos.
  9. La app separa credenciales sandbox y producción.
  10. La app tiene logs sin datos sensibles.
  11. La app maneja pagos rechazados.
  12. La app maneja pagos pendientes.
  13. La app maneja cancelaciones.
  14. La app maneja reembolsos o disputas si el negocio lo requiere.
  15. La app fue probada con webhooks repetidos.
  16. La app tiene política de cancelación y reembolso clara.
El mock sirve para aprender el patrón. La pasarela real define los detalles finales: endpoints, SDK, firma, eventos, estados, credenciales, restricciones y reglas comerciales.

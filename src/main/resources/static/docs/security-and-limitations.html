Seguridad y límites de StreamBox Demo

Esta guía explica qué límites tiene StreamBox Demo y qué cuidados debería tener un desarrollador al adaptar este patrón a una aplicación real.

StreamBox Demo es una aplicación educativa. Sirve para aprender el flujo de integración con una pasarela de pagos simulada, pero no debe usarse tal cual como aplicación productiva.

Qué es StreamBox Demo

StreamBox Demo representa una aplicación principal que vende planes de suscripción. Su objetivo es mostrar cómo una aplicación puede integrarse con Mock Payment Service.

Permite aprender:

  • Cómo crear una suscripción interna.
  • Cómo crear una preapproval en un proveedor de pagos simulado.
  • Cómo guardar IDs externos del proveedor.
  • Cómo separar la acción de suscribirse de la acción de pagar.
  • Cómo pagar una suscripción existente con tarjetas ficticias.
  • Cómo simular pagos aprobados, rechazados y pendientes.
  • Cómo recibir webhooks.
  • Cómo validar firmas de webhooks.
  • Cómo consultar el recurso actualizado al proveedor.
  • Cómo actualizar estados internos.
  • Cómo registrar eventos internos para entender el flujo.

Qué no es StreamBox Demo

StreamBox Demo no es una aplicación lista para producción.

No incluye:

  • Autenticación real de usuarios.
  • Autorización por roles.
  • Base de datos productiva.
  • Transacciones de base de datos.
  • Panel administrativo real.
  • Gestión real de clientes.
  • Facturación real.
  • Checkout real.
  • Control antifraude real.
  • Protección completa contra abuso.
  • Integración con una pasarela real.
  • Procesamiento de dinero real.

No usar tal cual en producción

StreamBox Demo debería usarse como material educativo, demo técnica o referencia de arquitectura. No debería exponerse públicamente como si fuera una aplicación comercial real.

Parte En la demo En producción
Usuarios Email escrito en formulario. Usuarios reales autenticados.
Planes Planes hardcodeados. Planes en base de datos o panel administrable.
Pagos Mock Payment Service. Proveedor real como Mercado Pago, Stripe, PayPal u otro.
Store Memoria o archivo local. Base de datos con transacciones.
Seguridad Configuración simple de demo. Autenticación, autorización, HTTPS, logs y controles.
Auditoría Eventos educativos. Auditoría persistente y consultable.

Tarjetas ficticias

Las tarjetas que aparecen en StreamBox son tarjetas ficticias para probar escenarios contra Mock Payment Service. En el flujo actual, se eligen en la acción Pagar, después de haber creado una suscripción con Suscribirme. 

4111111111111111
4000000000000002
4000000000009995
4000000000000069
4000000000000341
4000000000000259

No deben usarse tarjetas reales en StreamBox Demo.

En una aplicación real, lo ideal es no manejar números completos de tarjeta en el backend. Conviene usar checkout hospedado, tokenización o componentes seguros del proveedor de pagos.

Secrets y configuración

La demo usa un secret simple para validar webhooks: 

MOCK_PAYMENT_WEBHOOK_SECRET=dev-secret

Ese valor sirve para desarrollo local, pero no debería usarse en producción.

Buenas prácticas

  • No commitear secrets reales.
  • No hardcodear credenciales productivas.
  • Usar variables de entorno.
  • Separar credenciales de desarrollo, staging y producción.
  • Rotar secrets si se filtran.
  • No imprimir secrets en logs.
  • Usar secret managers cuando el proyecto crece.

Variables sensibles

MOCK_PAYMENT_WEBHOOK_SECRET
ACCESS_TOKEN_DEL_PROVEEDOR_REAL
SECRET_KEY_DEL_PROVEEDOR_REAL
WEBHOOK_SECRET_DEL_PROVEEDOR_REAL

Webhooks

StreamBox valida la firma de los webhooks antes de procesarlos. Esa es una buena práctica que sí conviene conservar en una aplicación real.

La demo valida:

  • Que exista data.id.
  • Que exista x-request-id.
  • Que exista x-signature.
  • Que la firma coincida con el secret compartido.

El patrón correcto es: 

Recibir webhook
  ↓
Validar firma
  ↓
Registrar evento recibido
  ↓
Consultar recurso actualizado al proveedor
  ↓
Actualizar estado interno

Qué reforzar en producción

  • Validar la firma según la documentación oficial del proveedor.
  • Validar antigüedad del timestamp si el proveedor lo permite.
  • Evitar replay attacks.
  • Implementar idempotencia fuerte.
  • Guardar eventos recibidos.
  • No procesar dos veces el mismo evento.
  • Responder 2xx solo cuando el evento fue aceptado correctamente.

Estado interno

StreamBox guarda su propio estado interno. Esta idea sí es importante para producción.

La aplicación principal no debería depender únicamente del panel o del estado externo de la pasarela.

StreamBox guarda

  • Suscripciones internas.
  • Pagos internos.
  • Webhooks recibidos.
  • Eventos internos.

Por qué importa

Porque una aplicación real necesita saber:

  • Qué usuario contrató qué plan.
  • Qué proveedor procesó el pago.
  • Cuál es el ID externo del pago.
  • Cuál es el ID externo de la suscripción.
  • Qué estado interno debe aplicar al negocio.
  • Qué pasó si un webhook falló.
  • Qué ocurrió ante un reclamo o investigación.

Persistencia

StreamBox Demo puede guardar estado en memoria o en archivo. 

DEMO_APP_STORAGE_TYPE=memory
DEMO_APP_STORAGE_TYPE=file

Con Docker, suele usarse: 

DEMO_APP_STORAGE_TYPE=file
DEMO_APP_STORAGE_FILE_PATH=/app/data/subscription-demo-state.bin

Y un volumen: 

./data:/app/data

Límite importante

Esta persistencia es solo para demo. No reemplaza una base de datos real.

En producción debería usarse:

  • Base de datos relacional o adecuada al dominio.
  • Repositorios.
  • Transacciones.
  • Migraciones.
  • Constraints únicos.
  • Backups.
  • Auditoría.

Datos personales

StreamBox Demo pide un email para simular el pagador. 

payerEmail

En una aplicación real, un email es un dato personal. También pueden ser datos personales:

  • Nombre.
  • Teléfono.
  • Dirección.
  • IP.
  • Historial de pagos.
  • Identificadores de cuenta.
  • Datos de facturación.

Buenas prácticas

  • Recolectar solo lo necesario.
  • Informar al usuario para qué se usan sus datos.
  • Proteger la base de datos.
  • No guardar datos sensibles innecesarios.
  • No loguear datos personales sin necesidad.
  • Definir política de retención.
  • Permitir baja o eliminación cuando corresponda.

Fraude y abuso

StreamBox Demo no tiene controles antifraude reales. Eso está bien para una demo, pero no sería suficiente en producción.

Riesgos en una aplicación real

  • Muchos intentos de pago fallidos.
  • Uso de tarjetas robadas.
  • Creación masiva de cuentas.
  • Abuso de promociones.
  • Contracargos.
  • Reclamos maliciosos.
  • Manipulación de endpoints.

Controles recomendados

  • Rate limiting.
  • Límites de intentos de pago.
  • Alertas ante actividad sospechosa.
  • Bloqueos temporales.
  • Revisión manual de casos críticos.
  • Uso de herramientas antifraude de la pasarela.
  • Registro de eventos de seguridad.

Al pasar a una pasarela real

Al reemplazar Mock Payment Service por una pasarela real, hay que revisar cuidadosamente la documentación oficial del proveedor.

Aspectos a cambiar

En la demo Con proveedor real
MockPaymentClient Cliente real o SDK oficial del proveedor.
WebhookSignatureVerifier Verificación de firma oficial del proveedor.
Tarjetas ficticias en la acción Pagar Checkout, tokenización o SDK seguro.
Estados simples Mapeo completo de estados externos a internos.
DemoStore Base de datos real.
Eventos educativos Auditoría y logs estructurados.

Regla importante

No adaptar solo el endpoint feliz.

También adaptar:
rechazos
pendientes
cancelaciones
reembolsos
contracargos
webhooks duplicados
webhooks fuera de orden
fallas del proveedor
timeouts
errores parciales

Checklist antes de usar este patrón en producción

  1. Agregar autenticación real.
  2. Agregar autorización por roles.
  3. Reemplazar DemoStore por base de datos.
  4. Agregar transacciones.
  5. Agregar migraciones.
  6. Guardar pagos y suscripciones con constraints únicos.
  7. Implementar idempotencia fuerte.
  8. Usar proveedor real o SDK oficial.
  9. Validar webhooks según documentación oficial.
  10. No guardar tarjetas reales.
  11. No usar dev-secret.
  12. Usar HTTPS.
  13. Agregar rate limiting.
  14. Agregar logs sin datos sensibles.
  15. Agregar auditoría de operaciones críticas.
  16. Definir política de privacidad.
  17. Definir términos y condiciones.
  18. Definir política de cancelación y reembolsos.
  19. Consultar requisitos legales, fiscales y de seguridad aplicables.
StreamBox Demo es útil como mapa. Para producción, el patrón debe reforzarse con seguridad, base de datos real, idempotencia, cumplimiento legal, monitoreo y una pasarela de pagos real.

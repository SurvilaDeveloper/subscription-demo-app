Referencia de endpoints de StreamBox Demo

Esta página resume los endpoints HTTP principales de StreamBox Demo. Sirve para probar la aplicación desde curl, Postman o desde otra herramienta sin depender exclusivamente de la UI.

StreamBox Demo representa la aplicación principal. Sus endpoints no son los mismos que los de Mock Payment Service. StreamBox guarda estado interno propio y llama al mock cuando necesita crear suscripciones, pagos o consultar recursos externos.

Base URL

Con el puerto por defecto: 

http://localhost:8080

Si publicaste StreamBox en otro puerto, por ejemplo 8085: 

http://localhost:8085

Información de integración

Devuelve la configuración real que StreamBox está usando para comunicarse con Mock Payment Service.

Ejemplo

curl http://localhost:8080/api/demo/info

Respuesta esperada en Docker

{
  "name": "subscription-demo-app",
  "public_base_url": "http://localhost:8080",
  "webhook_base_url": "http://subscription-demo-app:8080",
  "mock_payment_base_url": "http://mock-payment-service:9090",
  "webhook_path": "/api/webhooks/mock-payment",
  "webhook_url": "http://subscription-demo-app:8080/api/webhooks/mock-payment"
}

Para qué sirve

  • Confirmar si StreamBox llama al mock con la URL correcta.
  • Confirmar qué webhook URL le entrega StreamBox al mock.
  • Detectar errores de configuración con Docker o puertos.

Estado de la demo

Devuelve conteos y configuración de persistencia. 

GET /api/demo/state

Ejemplo

curl http://localhost:8080/api/demo/state

Respuesta de ejemplo

{
  "subscriptions_count": 1,
  "payments_count": 1,
  "events_count": 8,
  "received_webhooks_count": 1,
  "storage_type": "file",
  "state_file_path": "/app/data/subscription-demo-state.bin"
}

Resetear estado

DELETE /api/demo/state

Ejemplo

curl -X DELETE http://localhost:8080/api/demo/state

Esto borra el estado interno de StreamBox:

  • Suscripciones internas.
  • Pagos internos.
  • Eventos internos.
  • Webhooks recibidos.
  • Contadores internos.
Este reset no borra el estado de Mock Payment Service. Para borrar el estado del mock hay que usar Mock Payment Studio o DELETE /mock/state en el mock.

Crear suscripción

Crea una suscripción interna en StreamBox, crea una preapproval en Mock Payment Service y guarda el ID externo del proveedor. En este paso todavía no se genera el pago. 

POST /api/subscriptions

Body

{
  "plan_id": "basic",
  "payer_email": "cliente@test.com"
}

Ejemplo con curl

curl -X POST http://localhost:8080/api/subscriptions \
  -H "Content-Type: application/json" \
  -d '{
    "plan_id": "basic",
    "payer_email": "cliente@test.com"
  }'

Resultado esperado

subscription.status = PENDING
provider_subscription_id = mock-preapproval-1
provider_subscription_status = pending

Qué hace internamente

1. Valida el plan.
2. Crea DemoSubscription en PENDING.
3. Llama a Mock Payment Service.
4. Crea una preapproval.
5. Guarda providerSubscriptionId.
6. Deja la suscripción lista para pagar.
Este endpoint representa la acción Suscribirme de la UI. Crea la suscripción, pero no intenta cobrar todavía.

Pagar suscripción

Genera el pago inicial de una suscripción existente usando una tarjeta ficticia. Este endpoint requiere que la suscripción ya tenga un providerSubscriptionId. 

POST /api/subscriptions/{id}/pay

Body

{
  "card_number": "4111111111111111"
}

Ejemplo con curl

curl -X POST http://localhost:8080/api/subscriptions/demo-subscription-1/pay \
  -H "Content-Type: application/json" \
  -d '{
    "card_number": "4111111111111111"
  }'

Resultado esperado con tarjeta aprobada

subscription.status = ACTIVE
payment.status = APPROVED

Qué hace internamente

1. Busca la suscripción interna.
2. Verifica que tenga providerSubscriptionId.
3. Simula el pago con tarjeta ficticia.
4. Mock Payment Service crea un payment.
5. StreamBox guarda DemoPayment.
6. StreamBox actualiza el estado interno.
7. Mock Payment Service envía webhook.
8. StreamBox recibe y procesa el webhook.
Este endpoint representa la acción Pagar de la UI. La suscripción y el pago quedan separados para que el flujo sea más parecido a una integración real.

Endpoint combinado legacy

El endpoint anterior se conserva por compatibilidad y para pruebas rápidas. Crea la suscripción y simula el pago inicial en un solo request. 

POST /api/subscriptions/start

Body

{
  "plan_id": "basic",
  "payer_email": "cliente@test.com",
  "card_number": "4111111111111111"
}

Ejemplo con curl

curl -X POST http://localhost:8080/api/subscriptions/start \
  -H "Content-Type: application/json" \
  -d '{
    "plan_id": "basic",
    "payer_email": "cliente@test.com",
    "card_number": "4111111111111111"
  }'

La UI nueva no usa este endpoint como flujo principal. Usa POST /api/subscriptions para suscribirse y POST /api/subscriptions/{id}/pay para pagar.

Cambiar plan

Cambia el plan de una suscripción interna y sincroniza el cambio con Mock Payment Service. 

POST /api/subscriptions/{id}/change-plan

Body

{
  "plan_id": "pro"
}

Ejemplo

curl -X POST http://localhost:8080/api/subscriptions/demo-subscription-1/change-plan \
  -H "Content-Type: application/json" \
  -d '{
    "plan_id": "pro"
  }'

Resultado esperado

subscription.planId = pro
subscription.planName = Plan Pro

Resultado esperado

Webhook receiver

Endpoint usado por Mock Payment Service para avisar eventos a StreamBox. 

POST /api/webhooks/mock-payment

Este endpoint espera headers: 

x-request-id
x-signature

Y un payload con estructura parecida a: 

{
  "id": "mock-event-1",
  "live_mode": false,
  "type": "payment",
  "date_created": "2026-05-12T15:30:00Z",
  "user_id": "mock-user",
  "api_version": "v1",
  "action": "payment.created",
  "data": {
    "id": "mock-payment-1"
  }
}

Qué hace StreamBox al recibirlo

  1. Extrae x-request-id.
  2. Extrae x-signature.
  3. Extrae type, action y data.id.
  4. Valida la firma.
  5. Guarda el webhook recibido.
  6. Consulta el recurso actualizado en Mock Payment Service.
  7. Actualiza pagos o suscripciones internas.
  8. Marca el webhook como procesado o fallido.
Normalmente no se llama a este endpoint manualmente. Lo llama Mock Payment Service cuando ocurre un evento de pago o suscripción.

Errores frecuentes

Plan inexistente

Si se envía un plan_id que no existe, la suscripción no puede crearse. 

{
  "plan_id": "unknown",
  "payer_email": "cliente@test.com"
}

Usar uno de estos: 

basic
pro
enterprise

Suscripción inexistente

Si se llama una acción con un ID que no existe: 

POST /api/subscriptions/demo-subscription-999/cancel

StreamBox debería responder error porque no encuentra esa suscripción interna.

Mock Payment Service no disponible

Si POST /api/subscriptions falla al crear la preapproval, o si POST /api/subscriptions/{id}/pay falla al pagar, revisar:

  • Que Mock Payment Service esté levantado.
  • Que MOCK_PAYMENT_BASE_URL sea correcto.
  • Que ambos contenedores compartan red Docker.

Webhook no recibido

Si el pago aparece en Mock Payment Service pero no aparece como webhook recibido en StreamBox, revisar:

  • DEMO_APP_WEBHOOK_BASE_URL.
  • La tabla de webhooks salientes en Mock Payment Studio.
  • Si el webhook tiene delivered=true.
  • Si el endpoint /api/webhooks/mock-payment está disponible.

Firma inválida

Si el webhook llega pero no se procesa por firma inválida, revisar: 

MOCK_PAYMENT_WEBHOOK_SECRET

El valor debe coincidir en StreamBox Demo y en Mock Payment Service.

Para depurar una integración, los endpoints más útiles suelen ser /api/demo/info, /api/demo/webhooks, /api/demo/events y la tabla de webhooks salientes en Mock Payment Studio.

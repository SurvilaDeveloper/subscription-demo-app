Arquitectura interna de StreamBox Demo

Esta guía explica cómo está organizada StreamBox Demo por dentro. La aplicación representa un sistema principal que vende suscripciones y se integra con una pasarela de pagos simulada: Mock Payment Service.

La idea es entender qué responsabilidad tiene cada parte del proyecto: la UI, los controllers, los servicios, el cliente HTTP, los modelos internos, el store, los webhooks y la persistencia.

StreamBox Demo no es la pasarela de pagos. Es la aplicación que consume una pasarela. Por eso su arquitectura se parece a la que tendría una app real: estado interno propio, cliente hacia proveedor, webhook receiver, validación de firma y mapeo de estados.

StreamBox tiene dos responsabilidades principales:

  • Permitir iniciar y operar suscripciones desde una UI educativa.
  • Mostrar cómo una aplicación real debería mantener su propio estado interno al integrarse con un proveedor de pagos.

Capas principales

Capa Responsabilidad
UI estática Mostrar estado, formularios, tablas y acciones para operar la demo.
Controllers Exponer endpoints HTTP para la UI y para recibir webhooks.
Servicios Orquestar lógica de suscripciones, pagos, webhooks y cambios de estado.
Cliente del proveedor Encapsular llamadas HTTP hacia Mock Payment Service.
Modelos internos Representar suscripciones, pagos, webhooks recibidos y eventos internos.
Store interno Guardar estado en memoria o archivo para la demo.
Persistencia Conservar el estado local cuando se usa storage tipo archivo.

UI estática

La UI de StreamBox se sirve como archivos estáticos desde Spring Boot. Permite usar la aplicación sin abrir un IDE ni ejecutar comandos manuales.

Desde la UI se puede:

  • Ver el estado general de la aplicación principal.
  • Revisar la configuración de integración.
  • Crear una suscripción y después pagarla con tarjeta ficticia.
  • Simular cobros recurrentes.
  • Cambiar plan.
  • Cancelar una suscripción.
  • Ver suscripciones internas.
  • Ver pagos internos.
  • Ver webhooks recibidos.
  • Ver eventos internos.
  • Abrir documentación desde el menú Docs.
La UI no contiene la lógica importante de pagos. La UI llama endpoints de la aplicación y renderiza lo que el backend devuelve.

Controllers

Los controllers son la entrada HTTP de la aplicación. En StreamBox hay controllers para operar la demo y un controller dedicado para recibir webhooks.

Controller de suscripciones

El controller de suscripciones expone las acciones principales que consume la UI. El flujo actual separa la creación de la suscripción y el pago inicial. 

POST /api/subscriptions
POST /api/subscriptions/{id}/pay
POST /api/subscriptions/start
POST /api/subscriptions/{id}/simulate-recurring-charge
POST /api/subscriptions/{id}/change-plan
POST /api/subscriptions/{id}/cancel
Endpoint Uso
POST /api/subscriptions Crea la suscripción interna y la preapproval externa.
POST /api/subscriptions/{id}/pay Paga una suscripción existente con tarjeta ficticia.
POST /api/subscriptions/start Flujo combinado legacy: crea suscripción y paga en una sola llamada.

Controller de webhooks

src/main/java/com/survila/subscriptiondemo/controller/MockPaymentWebhookController.java

Este controller recibe eventos enviados por Mock Payment Service en: 

POST /api/webhooks/mock-payment

Su flujo conceptual es: 

Recibir request HTTP
  ↓
Extraer headers
  ↓
Extraer payload
  ↓
Validar firma
  ↓
Guardar webhook recibido
  ↓
Delegar procesamiento
  ↓
Marcar como procesado o fallido
  ↓
Responder al proveedor

Esta separación es importante porque el controller no debería concentrar toda la lógica de negocio. Su responsabilidad principal es recibir el request y delegar.

Servicios

El servicio más importante del flujo de pagos es: 

src/main/java/com/survila/subscriptiondemo/service/SubscriptionService.java

Este servicio orquesta casi todo el flujo de suscripciones y pagos: crea suscripciones internas, llama al proveedor, guarda IDs externos, paga suscripciones existentes, procesa webhooks y actualiza estados.

Responsabilidades principales

  • Crear una suscripción interna.
  • Crear una preapproval en Mock Payment Service.
  • Guardar el providerSubscriptionId.
  • Pagar una suscripción existente con tarjeta ficticia.
  • Simular cobros recurrentes.
  • Cambiar plan.
  • Cancelar suscripción.
  • Procesar webhooks.
  • Guardar pagos internos.
  • Mapear estados externos a estados internos.
  • Registrar eventos educativos.

Por qué centralizar esta lógica

Porque el flujo de pagos toca varias piezas al mismo tiempo: 

Plan interno
  ↓
Suscripción interna PENDING
  ↓
Preapproval externa
  ↓
Pago externo
  ↓
Pago interno
  ↓
Webhook
  ↓
Estado interno actualizado

Si esa lógica estuviera repartida sin orden entre controllers, UI y cliente HTTP, sería mucho más difícil de mantener.

Cliente del proveedor

La clase: 

src/main/java/com/survila/subscriptiondemo/client/MockPaymentClient.java

encapsula las llamadas HTTP hacia Mock Payment Service usando RestClient. Expone métodos como crear preapproval, consultar pago, pagar con tarjeta, simular cobro recurrente, cambiar plan y cancelar preapproval.

Qué problema resuelve

Evita que toda la aplicación tenga código como: 

POST /preapproval
GET /payment/{id}
POST /mock/preapproval/{id}/pay-with-card

disperso por distintos lugares.

En su lugar, el resto del sistema usa métodos con intención clara: 

createPreapproval(...)
getPayment(...)
payWithCard(...)
simulateRecurringCharge(...)
changePlan(...)
cancelPreapproval(...)

Equivalente en producción

En una aplicación real, esta capa podría convertirse en: 

PaymentProviderClient
MercadoPagoClient
StripeClient
PayPalClient

Incluso usando un SDK oficial, conviene mantener una capa propia para no acoplar toda la aplicación al proveedor.

Modelos internos

StreamBox no guarda solamente lo que devuelve Mock Payment Service. Tiene modelos internos propios.

DemoSubscription

src/main/java/com/survila/subscriptiondemo/model/DemoSubscription.java

Representa una suscripción desde el punto de vista de StreamBox. Guarda datos del plan, email del pagador, estado interno y el ID externo del proveedor.

Campo conceptual Uso
ID interno Identifica la suscripción dentro de StreamBox.
Plan Guarda el plan elegido por el usuario.
Monto y moneda Permite auditar qué se contrató.
Email Representa al pagador en la demo.
Provider subscription ID Relaciona la suscripción interna con la suscripción externa.
Status Estado interno usado por StreamBox.

DemoPayment

src/main/java/com/survila/subscriptiondemo/model/DemoPayment.java

Representa un pago interno creado a partir de un pago externo del proveedor. Guarda el ID interno, la suscripción asociada, el ID externo del pago, estado, detalle, monto, moneda y fecha.

DemoReceivedWebhook

src/main/java/com/survila/subscriptiondemo/model/DemoReceivedWebhook.java

Representa un webhook recibido por StreamBox. Guarda request ID, firma, tipo de evento, acción, data ID, payload recibido, si la firma fue válida, si fue procesado y el error si falló.

Idea importante

Proveedor externo ≠ estado interno de la aplicación

La aplicación principal necesita sus propias entidades para tomar decisiones de negocio.

Store interno

El store interno de la demo está en: 

src/main/java/com/survila/subscriptiondemo/store/DemoStore.java

Guarda suscripciones, pagos, eventos y webhooks recibidos. También genera IDs internos y puede persistir el estado en archivo cuando se usa storage tipo file.

Qué guarda

  • Suscripciones internas.
  • Pagos internos.
  • Eventos internos.
  • Webhooks recibidos.
  • Secuencias para generar IDs.

Búsquedas importantes

Para procesar webhooks, el store necesita buscar entidades internas usando IDs externos. 

findSubscriptionByProviderSubscriptionId(...)
findPaymentByProviderPaymentId(...)

Esto es clave porque los webhooks normalmente no traen IDs internos de la aplicación. Traen IDs del proveedor.

Arquitectura de webhooks

Los webhooks conectan el proveedor simulado con la aplicación principal. 

Mock Payment Service
  ↓
POST /api/webhooks/mock-payment
  ↓
MockPaymentWebhookController
  ↓
WebhookSignatureVerifier
  ↓
SubscriptionService.processWebhook(...)
  ↓
MockPaymentClient.getPayment(...)
  ↓
MockPaymentClient.getPreapproval(...)
  ↓
DemoStore

Validación de firma

La firma se valida en: 

src/main/java/com/survila/subscriptiondemo/service/WebhookSignatureVerifier.java

Esta clase reconstruye el manifest, calcula HMAC SHA-256 con el secret compartido y compara el hash esperado con el recibido.

Procesamiento

Una vez validado el webhook, StreamBox procesa dos tipos principales:

Evento Acción de StreamBox
payment.created Consulta el pago, guarda pago interno y actualiza la suscripción.
preapproval.updated Consulta la suscripción externa y actualiza la suscripción interna.
preapproval.cancelled Consulta la suscripción externa y marca el estado interno correspondiente.
La arquitectura correcta no es “recibir webhook y creer todo el body”. La arquitectura correcta es: recibir, validar, registrar, consultar al proveedor y recién ahí actualizar.

Persistencia

StreamBox puede trabajar en dos modos:

Modo Descripción
memory El estado vive en memoria y se pierde al reiniciar.
file El estado se guarda en un archivo local.

Configuración típica: 

DEMO_APP_STORAGE_TYPE=file
DEMO_APP_STORAGE_FILE_PATH=/app/data/subscription-demo-state.bin

En Docker se monta: 

./data:/app/data

Esta persistencia sirve para la demo. En producción debería reemplazarse por una base de datos.

Arquitectura con Docker

En Docker, StreamBox y Mock Payment Service pueden correr como contenedores separados. 

Navegador
  ↓
localhost:8080
  ↓
subscription-demo-app:8080
  ↓
mock-payment-service:9090

StreamBox llama al mock con: 

MOCK_PAYMENT_BASE_URL=http://mock-payment-service:9090

Mock Payment Service llama a StreamBox con: 

DEMO_APP_WEBHOOK_BASE_URL=http://subscription-demo-app:8080

Ambos servicios deben compartir la red: 

payment-demo-network

Qué cambiar en producción

La arquitectura de StreamBox sirve como mapa, pero una aplicación real necesita reforzar varias partes.

En StreamBox Demo En producción
UI estática educativa Frontend real con autenticación, permisos y validaciones.
DemoStore Base de datos con repositorios y transacciones.
Planes hardcodeados Planes administrables o persistidos.
MockPaymentClient Cliente real del proveedor o SDK oficial encapsulado.
WebhookSignatureVerifier del mock Verificación oficial de la pasarela real.
Eventos educativos Auditoría real, logs estructurados y monitoreo.
Idempotencia básica Constraints únicos, transacciones y control de duplicados.

Resumen

StreamBox Demo está organizado para mostrar el flujo completo de una aplicación que cobra suscripciones. 

UI
  ↓
Controllers
  ↓
SubscriptionService
  ↓
MockPaymentClient
  ↓
Mock Payment Service

Webhook
  ↓
Webhook controller
  ↓
Signature verifier
  ↓
SubscriptionService
  ↓
Store interno
Lo más valioso de esta arquitectura es la separación de responsabilidades: la UI muestra, el controller recibe, el servicio orquesta, el cliente habla con el proveedor, el verifier valida firmas y el store conserva el estado interno.

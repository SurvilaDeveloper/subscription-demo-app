Recorrido del código de pagos

Esta guía muestra el código principal que usa StreamBox Demo para integrarse con Mock Payment Service. Está pensada para poder entender la integración incluso si la aplicación se ejecuta desde una imagen Docker y no se abre el proyecto en un IDE.

Esta página no reemplaza el código fuente. Es un recorrido educativo: muestra los fragmentos más importantes, explica qué hace cada pieza y señala qué partes conviene adaptar en un proyecto real.

Mapa general del flujo

Usuario elige plan y tarjeta ficticia
  ↓
SubscriptionService.startSubscription(...)
  ↓
Crea DemoSubscription interna en PENDING
  ↓
MockPaymentClient.createPreapproval(...)
  ↓
Guarda providerSubscriptionId
  ↓
MockPaymentClient.payWithCard(...)
  ↓
Guarda DemoPayment interno
  ↓
Mock Payment Service envía webhook
  ↓
MockPaymentWebhookController.receiveWebhook(...)
  ↓
WebhookSignatureVerifier.verifyOrThrow(...)
  ↓
SubscriptionService.processWebhook(...)
  ↓
Consulta GET /payment/{id} y GET /preapproval/{id}
  ↓
Actualiza estado interno

La idea central es que StreamBox no confía solamente en el resultado visual del pago. También mantiene su propio estado interno, guarda IDs externos del proveedor, recibe webhooks, valida firma y consulta al proveedor para confirmar el estado actualizado.

1. MockPaymentClient.java

Este archivo concentra las llamadas HTTP hacia Mock Payment Service. Es una capa de integración con el proveedor simulado. 

src/main/java/com/survila/subscriptiondemo/client/MockPaymentClient.java

La clase usa RestClient y recibe la URL base desde configuración: 

@Component
public class MockPaymentClient {

    private final RestClient restClient;

    public MockPaymentClient(
            @Value("${demo-app.mock-payment.base-url:http://localhost:9090}") String baseUrl
    ) {
        this.restClient = RestClient.builder()
                .baseUrl(baseUrl)
                .build();
    }
}

Por qué existe esta clase

Para que el resto de la aplicación no tenga que conocer URLs, endpoints ni detalles HTTP del proveedor. En vez de llamar al mock desde cualquier servicio o controller, todo pasa por una clase dedicada. 

SubscriptionService
  ↓
MockPaymentClient
  ↓
Mock Payment Service

Métodos principales

public MockPreapprovalResponse createPreapproval(MockCreatePreapprovalRequest request) {
    return restClient.post()
            .uri("/preapproval")
            .body(request)
            .retrieve()
            .body(MockPreapprovalResponse.class);
}

public MockPaymentResponse getPayment(String id) {
    return restClient.get()
            .uri("/payment/{id}", id)
            .retrieve()
            .body(MockPaymentResponse.class);
}

public MockPayWithCardResponse payWithCard(String preapprovalId, MockPayWithCardRequest request) {
    return restClient.post()
            .uri("/mock/preapproval/{id}/pay-with-card", preapprovalId)
            .body(request)
            .retrieve()
            .body(MockPayWithCardResponse.class);
}

Qué representa en una app real

En una aplicación real esta clase podría reemplazarse por: 

MercadoPagoClient
StripeClient
PayPalClient
PaymentProviderClient

La idea importante no es el nombre MockPaymentClient, sino el patrón: aislar el código que habla con la pasarela.

2. SubscriptionService.java

Este es el corazón del flujo de pagos de StreamBox Demo. 

src/main/java/com/survila/subscriptiondemo/service/SubscriptionService.java

El servicio recibe el store interno, el catálogo de planes, el cliente del mock y dos URLs configurables: la URL pública de StreamBox y la URL base para recibir webhooks. 

@Service
public class SubscriptionService {

    private final DemoStore store;
    private final PlanCatalogService planCatalogService;
    private final MockPaymentClient mockPaymentClient;
    private final String publicBaseUrl;
    private final String webhookBaseUrl;

    public SubscriptionService(
            DemoStore store,
            PlanCatalogService planCatalogService,
            MockPaymentClient mockPaymentClient,
            @Value("${demo-app.public-base-url:http://localhost:8080}") String publicBaseUrl,
            @Value("${demo-app.webhook-base-url:http://localhost:8080}") String webhookBaseUrl
    ) {
        this.store = store;
        this.planCatalogService = planCatalogService;
        this.mockPaymentClient = mockPaymentClient;
        this.publicBaseUrl = publicBaseUrl;
        this.webhookBaseUrl = webhookBaseUrl;
    }
}

Por qué existe este servicio

Porque la integración de pagos no es solo “llamar a un endpoint”. Hay que orquestar varias cosas:

  • Validar el plan.
  • Crear estado interno.
  • Llamar al proveedor.
  • Guardar IDs externos.
  • Simular o procesar pagos.
  • Guardar pagos internos.
  • Procesar webhooks.
  • Mapear estados externos a estados internos.

3. Crear y pagar una suscripción

El método startSubscription representa el flujo inicial cuando el usuario elige un plan y paga. 

public StartSubscriptionResponse startSubscription(StartSubscriptionRequest request) {
    Plan plan = planCatalogService.findById(request.planId())
            .orElseThrow(() -> new BadRequestException("Plan not found: " + request.planId()));

    Instant now = Instant.now();

    DemoSubscription subscription = new DemoSubscription(
            store.nextSubscriptionId(),
            plan.id(),
            plan.name(),
            plan.amount(),
            plan.currency(),
            request.payerEmail(),
            null,
            SubscriptionStatus.PENDING,
            now,
            now
    );

    store.saveSubscription(subscription);

    MockPreapprovalResponse preapproval = mockPaymentClient.createPreapproval(
            buildCreatePreapprovalRequest(subscription)
    );

    subscription.setProviderSubscriptionId(preapproval.id());
    store.saveSubscription(subscription);

    MockPayWithCardResponse payResponse = mockPaymentClient.payWithCard(
            preapproval.id(),
            buildPayWithCardRequest(request.cardNumber())
    );

    subscription.setStatus(mapPreapprovalStatus(payResponse.preapprovalStatus()));
    store.saveSubscription(subscription);

    DemoPayment payment = savePaymentIfMissing(
            subscription.getId(),
            payResponse.payment()
    );

    return new StartSubscriptionResponse(
            subscription,
            payment,
            preapproval.id(),
            payResponse.payment().id(),
            payResponse.preapprovalStatus(),
            payResponse.payment().status()
    );
}

Qué está pasando paso a paso

  1. Busca el plan elegido.
  2. Crea una suscripción interna en estado PENDING.
  3. Guarda la suscripción en el store.
  4. Llama a Mock Payment Service para crear una preapproval.
  5. Guarda el ID externo del proveedor en providerSubscriptionId.
  6. Simula el pago con tarjeta ficticia.
  7. Mapea el estado del proveedor a un estado interno.
  8. Guarda el pago interno si todavía no existe.
  9. Devuelve una respuesta educativa con datos internos y externos.

Pedido enviado al proveedor

StreamBox arma el request hacia Mock Payment Service con el plan, email, monto, moneda, URL pública y endpoint de webhook: 

private MockCreatePreapprovalRequest buildCreatePreapprovalRequest(DemoSubscription subscription) {
    return new MockCreatePreapprovalRequest(
            subscription.getPlanName(),
            "demo_subscription_id=" + subscription.getId(),
            subscription.getPayerEmail(),
            new MockCreatePreapprovalRequest.AutoRecurringRequest(
                    1,
                    "months",
                    subscription.getAmount(),
                    subscription.getCurrency()
            ),
            publicBaseUrl,
            webhookBaseUrl + "/api/webhooks/mock-payment"
    );
}

La parte clave es: 

webhookBaseUrl + "/api/webhooks/mock-payment"

Esa URL es donde Mock Payment Service va a enviar los webhooks.

4. Simular cobro recurrente

Este método representa un pago posterior sobre una suscripción existente. 

public SubscriptionActionResponse simulateRecurringCharge(
        String subscriptionId,
        SimulateRecurringChargeRequest request
) {
    DemoSubscription subscription = getSubscriptionOrThrow(subscriptionId);

    ensureProviderSubscription(subscription);

    MockPayWithCardResponse response = mockPaymentClient.simulateRecurringCharge(
            subscription.getProviderSubscriptionId(),
            new MockSimulateRecurringChargeRequest(
                    request.cardNumber(),
                    true
            )
    );

    subscription.setStatus(mapPreapprovalStatus(response.preapprovalStatus()));
    store.saveSubscription(subscription);

    DemoPayment payment = savePaymentIfMissing(
            subscription.getId(),
            response.payment()
    );

    return new SubscriptionActionResponse(
            subscription,
            payment,
            subscription.getProviderSubscriptionId(),
            response.payment().id(),
            response.preapprovalStatus(),
            response.payment().status()
    );
}

Qué enseña este método

Una suscripción no termina en el alta inicial. En sistemas reales puede haber renovaciones, cobros mensuales, pagos fallidos y cambios de estado posteriores.

5. Cambiar plan

El método changePlan muestra cómo StreamBox cambia el plan interno y también informa el cambio al proveedor simulado. 

public SubscriptionActionResponse changePlan(
        String subscriptionId,
        ChangeSubscriptionPlanRequest request
) {
    DemoSubscription subscription = getSubscriptionOrThrow(subscriptionId);

    ensureProviderSubscription(subscription);

    Plan newPlan = planCatalogService.findById(request.planId())
            .orElseThrow(() -> new BadRequestException("Plan not found: " + request.planId()));

    mockPaymentClient.changePlan(
            subscription.getProviderSubscriptionId(),
            new MockChangePlanRequest(
                    newPlan.name(),
                    new MockCreatePreapprovalRequest.AutoRecurringRequest(
                            1,
                            "months",
                            newPlan.amount(),
                            newPlan.currency()
                    ),
                    true
            )
    );

    MockPreapprovalResponse providerPreapproval = mockPaymentClient.getPreapproval(
            subscription.getProviderSubscriptionId()
    );

    subscription.replacePlan(newPlan);
    subscription.setStatus(mapPreapprovalStatus(providerPreapproval.status()));
    store.saveSubscription(subscription);

    return new SubscriptionActionResponse(
            subscription,
            null,
            subscription.getProviderSubscriptionId(),
            null,
            providerPreapproval.status(),
            null
    );
}

Por qué consulta al proveedor después del cambio

Después de pedir el cambio, StreamBox consulta la preapproval actualizada. Esa es una idea muy buena: ante un cambio importante, no conviene asumir el estado final solamente por haber llamado al endpoint.

6. Cancelar suscripción

Este método cancela la suscripción en el proveedor y luego consulta el estado actualizado. 

public SubscriptionActionResponse cancelSubscription(String subscriptionId) {
    DemoSubscription subscription = getSubscriptionOrThrow(subscriptionId);

    ensureProviderSubscription(subscription);

    mockPaymentClient.cancelPreapproval(
            subscription.getProviderSubscriptionId(),
            new MockSubscriptionActionRequest(true)
    );

    MockPreapprovalResponse providerPreapproval = mockPaymentClient.getPreapproval(
            subscription.getProviderSubscriptionId()
    );

    subscription.setStatus(mapPreapprovalStatus(providerPreapproval.status()));
    store.saveSubscription(subscription);

    return new SubscriptionActionResponse(
            subscription,
            null,
            subscription.getProviderSubscriptionId(),
            null,
            providerPreapproval.status(),
            null
    );
}

Qué enseña este método

La cancelación debe quedar reflejada en los dos lados: 

Aplicación principal
Proveedor de pagos

7. MockPaymentWebhookController.java

Este controller recibe los webhooks que Mock Payment Service envía hacia StreamBox. 

src/main/java/com/survila/subscriptiondemo/controller/MockPaymentWebhookController.java
@RestController
@RequestMapping("/api/webhooks/mock-payment")
public class MockPaymentWebhookController {

    private final WebhookSignatureVerifier signatureVerifier;
    private final SubscriptionService subscriptionService;
    private final DemoStore store;

    @PostMapping
    public ResponseEntity<Void> receiveWebhook(
            @RequestHeader(value = "x-request-id", required = false) String requestId,
            @RequestHeader(value = "x-signature", required = false) String signature,
            @RequestBody(required = false) MockPaymentWebhookPayload payload
    ) {
        ...
    }
}

Qué hace este controller

  1. Recibe el webhook.
  2. Extrae x-request-id.
  3. Extrae x-signature.
  4. Extrae type, action y data.id.
  5. Valida la firma.
  6. Guarda el webhook recibido.
  7. Delega el procesamiento a SubscriptionService.
  8. Marca el webhook como procesado o fallido.

Fragmento clave

signatureVerifier.verifyOrThrow(
        dataId,
        requestId,
        signature
);

receivedWebhook = new DemoReceivedWebhook(
        store.nextReceivedWebhookId(),
        requestId,
        signature,
        type,
        action,
        dataId,
        true,
        false,
        null,
        Instant.now()
);

store.saveReceivedWebhook(receivedWebhook);

subscriptionService.processWebhook(payload);

receivedWebhook.markProcessed();
store.saveReceivedWebhook(receivedWebhook);

return ResponseEntity.ok().build();

Por qué está bien separado

El controller no resuelve toda la lógica de negocio. Su trabajo es recibir HTTP, validar seguridad básica, registrar el evento y delegar. 

Controller
  ↓
WebhookSignatureVerifier
  ↓
SubscriptionService
  ↓
DemoStore / MockPaymentClient

Validaciones principales

public void verifyOrThrow(String dataId, String requestId, String signatureHeader) {
    if (dataId == null || dataId.isBlank()) {
        throw new BadRequestException("Missing data.id in webhook payload.");
    }

    if (requestId == null || requestId.isBlank()) {
        throw new BadRequestException("Missing x-request-id header.");
    }

    if (signatureHeader == null || signatureHeader.isBlank()) {
        throw new BadRequestException("Missing x-signature header.");
    }

    String timestampValue = extractSignaturePart(signatureHeader, "ts");
    String receivedHash = extractSignaturePart(signatureHeader, "v1");

    ...
}

Manifest firmado

La firma se calcula usando el mismo formato que Mock Payment Service: 

private String createHash(String dataId, String requestId, long timestamp) {
    String manifest = "id:%s;request-id:%s;ts:%d;"
            .formatted(dataId, requestId, timestamp);

    return hmacSha256Hex(webhookSecret, manifest);
}

Comparación segura

boolean valid = MessageDigest.isEqual(
        expectedHash.getBytes(StandardCharsets.UTF_8),
        receivedHash.getBytes(StandardCharsets.UTF_8)
);

if (!valid) {
    throw new BadRequestException("Invalid webhook signature.");

En producción, la validación exacta depende de la pasarela real. Mercado Pago, Stripe, PayPal u otros proveedores pueden usar headers, secretos, certificados o esquemas distintos. El patrón importante es no procesar webhooks sin validarlos.

9. Procesamiento de webhooks

Una vez validado el webhook, el controller llama a: 

subscriptionService.processWebhook(payload);

El servicio distingue eventos de pago y eventos de suscripción: 

public void processWebhook(MockPaymentWebhookPayload payload) {
    if (payload == null || payload.data() == null || payload.data().id() == null) {
        throw new BadRequestException("Invalid webhook payload.");
    }

    if ("payment".equals(payload.type()) && "payment.created".equals(payload.action())) {
        processPaymentCreatedWebhook(payload.data().id());
        return;
    }

    if ("preapproval".equals(payload.type())) {
        processPreapprovalWebhook(payload.action(), payload.data().id());
        return;
    }

    store.addEvent(
            "WEBHOOK_IGNORED",
            "Webhook ignored: unsupported type/action %s/%s."
                    .formatted(payload.type(), payload.action())
    );
}

Webhook de pago

Para un pago, StreamBox no se queda solamente con el body del webhook. Consulta el pago al proveedor: 

private void processPaymentCreatedWebhook(String providerPaymentId) {
    MockPaymentResponse providerPayment = mockPaymentClient.getPayment(providerPaymentId);

    DemoSubscription subscription = store.findSubscriptionByProviderSubscriptionId(
            providerPayment.preapprovalId()
    ).orElseThrow(...);

    DemoPayment payment = savePaymentIfMissing(subscription.getId(), providerPayment);

    MockPreapprovalResponse providerPreapproval = mockPaymentClient.getPreapproval(
            providerPayment.preapprovalId()
    );

    subscription.setStatus(mapPreapprovalStatus(providerPreapproval.status()));
    store.saveSubscription(subscription);
}

Idea clave

Webhook recibido
  ↓
Validar firma
  ↓
Consultar recurso actualizado al proveedor
  ↓
Actualizar estado interno

Esta es una de las ideas más importantes de toda la demo.

    private final String requestId;
    private final String signature;

En producción, este modelo podría convertirse en una tabla de auditoría de webhooks.

Búsqueda por ID externo

Esta búsqueda es clave para procesar webhooks. El webhook trae IDs del proveedor, no IDs internos. 

public Optional<DemoSubscription> findSubscriptionByProviderSubscriptionId(String providerSubscriptionId) {
    return subscriptions.values()
            .stream()
            .filter(subscription -> providerSubscriptionId.equals(subscription.getProviderSubscriptionId()))
            .findFirst();
}

public Optional<DemoPayment> findPaymentByProviderPaymentId(String providerPaymentId) {
    return payments.values()
            .stream()
            .filter(payment -> providerPaymentId.equals(payment.getProviderPaymentId()))
            .findFirst();
}

12. Qué cambiar en producción

En StreamBox Demo En proyecto real
MockPaymentClient Cliente real del proveedor o interfaz PaymentProviderClient.
DemoStore Base de datos, repositorios, transacciones y migraciones.
DemoSubscription Entidad real como BusinessSubscription.
DemoPayment Entidad real como BusinessPayment o PaymentTransaction.
DemoReceivedWebhook Tabla real de webhooks recibidos con idempotencia.
Tarjetas ficticias Checkout hospedado, tokenización o SDK seguro del proveedor.
Planes hardcodeados Planes en base de datos o configurables desde administración.
Estados simples Estados internos bien definidos y reglas de negocio completas.

Checklist de adaptación

Crear entidades reales.
Crear repositories.
Crear migraciones.
Agregar transacciones.
Agregar idempotencia en webhooks.
Guardar payload raw si corresponde.
Validar firma según la pasarela real.
Usar SDK oficial o HTTP client robusto.
Manejar timeouts y errores.
No guardar tarjetas reales.
Agregar logs y auditoría.
Separar credenciales por ambiente.
Agregar tests automatizados.

Resumen final

El código de pagos de StreamBox Demo enseña una arquitectura pequeña pero muy importante: 

Cliente del proveedor
  ↓
Servicio de billing
  ↓
Estado interno propio
  ↓
Webhook receiver
  ↓
Validador de firma
  ↓
Consulta posterior al proveedor
  ↓
Mapeo de estados
  ↓
Auditoría interna
El objetivo no es copiar StreamBox Demo tal cual. El objetivo es entender el patrón y adaptarlo a una aplicación real con base de datos, seguridad, transacciones, idempotencia y una pasarela de pagos real.

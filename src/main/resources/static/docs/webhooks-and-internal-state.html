Webhooks y estado interno en StreamBox Demo

Esta guía explica cómo StreamBox Demo recibe webhooks desde Mock Payment Service, cómo valida que el evento sea confiable y cómo actualiza su propio estado interno.

La idea principal es que StreamBox representa una aplicación real. Por eso no alcanza con que Mock Payment Service diga que un pago ocurrió: StreamBox necesita registrar el evento, validar la firma, consultar al proveedor y actualizar sus propias suscripciones y pagos.

El webhook se trata como un aviso. StreamBox no debería confiar ciegamente en el body recibido. Después de validar la firma, consulta a Mock Payment Service para obtener el recurso actualizado.

Idea central

Mock Payment Service
  ↓ envía webhook firmado
StreamBox Demo
  ↓ valida firma
StreamBox Demo
  ↓ registra webhook recibido
StreamBox Demo
  ↓ consulta pago o suscripción al proveedor
StreamBox Demo
  ↓ actualiza estado interno
StreamBox Demo
  ↓ registra eventos educativos

Esto permite que StreamBox tenga una vista propia del mundo:

  • Suscripciones internas.
  • Pagos internos.
  • Webhooks recibidos.
  • Eventos internos.

Flujo completo

Un flujo típico de pago aprobado funciona así: 

1. El usuario elige un plan y presiona Suscribirme.
2. StreamBox crea una suscripción interna PENDING.
3. StreamBox llama a Mock Payment Service y crea una preapproval.
4. Mock Payment Service devuelve providerSubscriptionId.
5. StreamBox guarda providerSubscriptionId.
6. La suscripción queda lista para pagar.
7. El usuario selecciona la suscripción y presiona Pagar.
8. StreamBox simula el pago con tarjeta ficticia.
9. Mock Payment Service crea un payment.
10. Mock Payment Service envía webhook a StreamBox.
11. StreamBox recibe el webhook.
12. StreamBox valida x-signature.
13. StreamBox registra DemoReceivedWebhook.
14. StreamBox consulta GET /payment/{id}.
15. StreamBox consulta GET /preapproval/{id}.
16. StreamBox crea o actualiza DemoPayment.
17. StreamBox actualiza DemoSubscription.
18. StreamBox marca el webhook como procesado.
La creación de la suscripción y el pago son acciones separadas en la UI. El webhook aparece normalmente después del paso Pagar, porque ahí se genera el payment.

Endpoint receptor

StreamBox recibe webhooks en este endpoint: 

POST /api/webhooks/mock-payment

Cuando StreamBox corre en Docker, Mock Payment Service debe llamar a: 

http://subscription-demo-app:8080/api/webhooks/mock-payment

Cuando StreamBox corre directamente en la máquina host y Mock Payment Service corre en Docker, el webhook debería apuntar a: 

http://host.docker.internal:8080/api/webhooks/mock-payment
Si ambos servicios corren en Docker, no uses localhost para el webhook. Desde el contenedor de Mock Payment Service, localhost significa el propio contenedor del mock, no StreamBox.

Headers esperados

Mock Payment Service envía dos headers importantes: 

x-request-id
x-signature
Header Uso en StreamBox
x-request-id Identifica la entrega y participa en el cálculo de la firma.
x-signature Permite validar que el webhook fue firmado con el secret compartido.

Validación de firma

StreamBox usa el mismo secret que Mock Payment Service: 

MOCK_PAYMENT_WEBHOOK_SECRET=dev-secret

La firma tiene este formato: 

ts={timestamp},v1={hash}

El hash se calcula sobre este manifest: 

id:{data.id};request-id:{x-request-id};ts:{timestamp};

Ejemplo: 

id:mock-payment-1;request-id:a55b9e5d-c85d-4f68-aa74-2eec788e2eb4;ts:1778212356;

Qué valida StreamBox

  1. Que exista data.id.
  2. Que exista x-request-id.
  3. Que exista x-signature.
  4. Que el header tenga ts.
  5. Que el header tenga v1.
  6. Que el timestamp sea un número válido.
  7. Que el hash calculado coincida con el hash recibido.

Registro del webhook recibido

StreamBox guarda cada webhook recibido como un registro interno. 

DemoReceivedWebhook

Ese registro guarda:

Campo Uso
id ID interno del webhook recibido.
requestId ID de entrega enviado por Mock Payment Service.
signature Firma recibida en el header.
type Tipo de evento: payment o preapproval.
action Acción del evento, por ejemplo payment.created.
dataId ID del recurso externo afectado.
validSignature Indica si la firma fue válida.
processed Indica si StreamBox pudo procesar el evento.
error Mensaje de error si el procesamiento falló.
receivedAt Fecha de recepción.

Procesamiento del webhook

Una vez validada la firma, StreamBox delega el procesamiento al servicio de suscripciones. 

subscriptionService.processWebhook(payload);

El servicio distingue dos grandes tipos de eventos:

type action Qué hace StreamBox
payment payment.created Consulta el pago, guarda pago interno y actualiza suscripción.
preapproval preapproval.updated Consulta la suscripción externa y actualiza la suscripción interna.
preapproval preapproval.cancelled Consulta la suscripción externa y marca la suscripción interna como cancelada.

Evento payment.created

Cuando llega un evento: 

type=payment
action=payment.created

StreamBox usa data.id como ID externo del pago. 

data.id = mock-payment-1

Luego consulta: 

GET /payment/mock-payment-1

Con la respuesta del proveedor:

  1. Obtiene el preapprovalId asociado al pago.
  2. Busca la suscripción interna por providerSubscriptionId.
  3. Guarda el pago interno si todavía no existe.
  4. Consulta la suscripción externa actualizada.
  5. Mapea el estado externo a estado interno.
  6. Actualiza la suscripción interna.
provider payment id
  ↓
provider preapproval id
  ↓
internal subscription
  ↓
internal payment
  ↓
internal subscription status

Eventos preapproval

Cuando llega un evento de suscripción externa: 

type=preapproval

StreamBox usa data.id como ID externo de la suscripción. 

data.id = mock-preapproval-1

Luego consulta: 

GET /preapproval/mock-preapproval-1

Con esa respuesta:

  1. Busca la suscripción interna por providerSubscriptionId.
  2. Mapea el estado externo.
  3. Actualiza la suscripción interna.
  4. Registra un evento educativo.

Mapeo de estado interno

Mock Payment Service tiene sus propios estados. StreamBox los convierte a estados internos.

Estado del proveedor Estado interno en StreamBox
pending PENDING
authorized ACTIVE
payment_failed PAYMENT_FAILED
paused PAUSED
cancelled CANCELLED

También mapea estados de pago:

Estado del proveedor Estado interno en StreamBox
approved APPROVED
rejected REJECTED
in_process IN_PROCESS
Otro valor UNKNOWN
Este mapeo es una práctica importante. Una aplicación real no debería depender en todo su código del vocabulario exacto de una pasarela externa.

Idempotencia

Un webhook puede llegar más de una vez. Por eso StreamBox evita duplicar pagos usando el ID externo. 

findPaymentByProviderPaymentId(providerPayment.id())

Si el pago ya existe, no crea otro pago interno. 

Webhook repetido
  ↓
Mismo providerPaymentId
  ↓
No duplicar DemoPayment

Esta idea es clave para producción. En un sistema real conviene reforzarla con constraints únicos en base de datos. 

UNIQUE(provider_payment_id)
UNIQUE(provider_event_id)
UNIQUE(request_id)

Errores comunes

Firma inválida

Causa frecuente: 

MOCK_PAYMENT_WEBHOOK_SECRET diferente entre StreamBox y Mock Payment Service

Ambos deben usar el mismo valor: 

MOCK_PAYMENT_WEBHOOK_SECRET=dev-secret

Webhook no llega

Si Mock Payment Studio muestra delivered=false, revisar el webhook URL generado por StreamBox.

Si ambos servicios corren en Docker, debe ser: 

http://subscription-demo-app:8080/api/webhooks/mock-payment

No: 

http://localhost:8080/api/webhooks/mock-payment

Webhook llega pero no se procesa

Revisar la tabla: 

Webhooks recibidos por StreamBox

Ahí se puede ver:

  • Si la firma fue válida.
  • Si fue procesado.
  • Qué error ocurrió.
  • Qué type, action y dataId llegaron.

No encuentra suscripción interna

Puede pasar si Mock Payment Service envía un webhook de una preapproval que StreamBox no creó o no tiene registrada. 

Internal subscription not found for provider subscription

En producción, este tipo de error debería quedar registrado para investigación.

Qué mirar en la UI de StreamBox

Después de una prueba con pago y webhook, revisar estas secciones:

Sección Qué muestra
Suscripciones internas Estado interno de cada suscripción.
Pagos internos Pagos registrados luego de consultar al proveedor.
Webhooks recibidos por StreamBox Firma, procesamiento, error y metadata del webhook.
Eventos internos Historia educativa de lo que hizo StreamBox.
Configuración de integración URLs y secret usados para integrarse con el mock.

Qué cambiar en producción

El patrón de StreamBox sirve como referencia, pero en una aplicación real conviene reforzarlo.

En StreamBox Demo En producción
DemoStore Base de datos con transacciones.
Listas y maps en memoria Repositorios, constraints e índices.
Validación HMAC del mock Validación oficial de la pasarela real.
Eventos internos simples Auditoría y logs estructurados.
Idempotencia básica por providerPaymentId Idempotencia reforzada en base de datos.
Estados simplificados Estados de dominio completos y reglas de negocio.

Checklist para probar webhooks

  1. Mock Payment Service está levantado.
  2. StreamBox Demo está levantado.
  3. Ambos servicios comparten red Docker si corren en contenedores.
  4. MOCK_PAYMENT_BASE_URL apunta a http://mock-payment-service:9090.
  5. DEMO_APP_WEBHOOK_BASE_URL apunta a http://subscription-demo-app:8080.
  6. El secret coincide en ambos servicios.
  7. Se creó una suscripción desde StreamBox.
  8. Se pagó con tarjeta ficticia.
  9. Mock Payment Studio muestra delivered=true.
  10. StreamBox muestra el webhook recibido.
  11. La firma aparece válida.
  12. El webhook aparece procesado.
  13. La suscripción interna cambió de estado.
  14. El pago interno fue registrado.
Si todo esto se cumple, el flujo de webhooks entre Mock Payment Service y StreamBox Demo está funcionando correctamente.
